Note méthodologique

Migration d'une plateforme analytique cloud vers une pile locale dbt + DuckDB

Cas d'étude : projet telecom-project-main (Rebtel) · Réalisé les 11 et 12 octobre 2026 · Dossier cible : Modernizing_Rebtel/rebtel_local/
Résumé Ce document décrit la reproduction, sur un poste de travail, d'une chaîne de données conçue pour Google Cloud Platform (Pub/Sub, Cloud Storage, BigQuery). La démarche suit quatre temps : l'étude de l'existant, la définition d'une architecture cible locale, la mise en œuvre par couches (ingestion, transformation, apprentissage automatique, restitution) et la vérification. Le pipeline local reproduit les 13 modèles d'origine. Il passe 38 tests de qualité de données et alimente le modèle de détection de fraude ainsi que le tableau de bord Streamlit. La procédure est d'abord présentée de façon générique, pour pouvoir être réutilisée sur un autre cas d'usage.

1Introduction et objectifs

Le projet d'origine est une plateforme d'analyse pour un opérateur qui propose à la fois des appels internationaux et des transferts d'argent. Il croise quatre domaines (appels, transferts, paiements, tickets de support) pour produire un classement du risque de fraude, un profil client unifié, des indicateurs de revenus et un suivi de la qualité réseau.

L'objectif de ce travail est double. Il s'agit d'abord de faire fonctionner cette chaîne sans aucun service cloud, avec des outils locaux et des répertoires qui jouent le rôle de stockage. Il s'agit ensuite d'en tirer une procédure reproductible, applicable à d'autres projets construits sur le même schéma.

Trois principes ont guidé le travail :

  • Fidélité. La logique métier est conservée à l'identique. Seule la syntaxe propre au moteur change.
  • Traçabilité. Chaque écart avec l'original est documenté, y compris les défauts conservés volontairement.
  • Vérifiabilité. Chaque étape se termine par une exécution et une mesure.

2Procédure générique en huit étapes

La démarche ci-dessous ne dépend pas du domaine télécom. Elle s'applique à tout projet de type ELT (extraction, chargement, transformation) hébergé dans un entrepôt cloud et que l'on souhaite exécuter localement.

  1. Inventorier l'existantLister les sources (format, volume, clés), les scripts, les services cloud utilisés et les modèles de transformation. Profiler les données brutes : nombre de lignes, clés distinctes, valeurs des colonnes catégorielles.
  2. Repérer les écarts entre documentation et codeComparer ce que le README annonce avec ce que le dépôt contient réellement. Ne migrer que ce qui existe.
  3. Faire la correspondance cloud vers localAssocier chaque service à un équivalent local : file de messages et stockage objet deviennent des répertoires, l'entrepôt devient DuckDB, l'orchestration SQL devient un projet dbt.
  4. Créer les zones de stockageUn répertoire par couche : raw/ pour les fichiers tels quels, staging/ pour les données nettoyées, marts/ pour les agrégats métier.
  5. Écrire l'ingestionUn script simple et idempotent qui dépose les fichiers sources dans raw/.
  6. Construire le projet dbtDéclarer les sources, traduire chaque modèle SQL dans le dialecte DuckDB, remplacer les noms de tables en dur par ref() et source(), écrire chaque modèle en Parquet.
  7. Ajouter des tests de donnéesUnicité et non-nullité des clés, valeurs acceptées pour chaque catégorie calculée.
  8. Rebrancher les consommateursModifier uniquement la couche d'accès aux données des scripts d'apprentissage et des tableaux de bord. Exécuter, mesurer, documenter.
Principe directeurOn modifie la couche d'accès aux données, jamais la logique métier. C'est ce qui permet de comparer le résultat local avec le résultat d'origine.

3.3 Modèles de transformation

Treize modèles répartis en trois couches : quatre modèles de staging (nettoyage, typage, catégories dérivées), quatre tables de faits agrégées par utilisateur, et cinq marts analytiques (prévention de la fraude, client 360, revenus, qualité réseau, corridors de transfert).

3.4 Constats

Constat principalLe dépôt ne contient pas de véritable projet dbt. dbt_runner.py est un script Python qui envoie des requêtes CREATE OR REPLACE TABLE à BigQuery dans un ordre écrit à la main. Il n'y a ni ref(), ni graphe de dépendances calculé, ni tests.
  • Le README mentionne des vues vw_*, un script looker_dashboard_creator.py et un dossier ml_outputs/. Aucun de ces éléments n'est présent dans le dépôt. Ils n'ont donc pas été recréés.
  • La colonne latest_subscription_plan est calculée avec MAX(), c'est-à-dire l'ordre alphabétique, et non le plan le plus récent. Ce comportement a été conservé pour rester fidèle.

Le choix de Parquet comme format de sortie permet à n'importe quel outil (pandas, DuckDB, Power BI, Spark) de lire les couches sans passer par la base. Le fichier DuckDB ne contient que des vues qui pointent vers ces fichiers.

5Mise en œuvre pas à pas

5.1 Ingestion vers la zone brute

Le script scripts/ingest_raw.py copie les quatre fichiers de telecom-project-main/data/ vers storage/raw/. Il remplace à lui seul le trajet Pub/Sub, Cloud Storage puis chargement BigQuery. Il est idempotent : le relancer produit le même état.

FILES = {
    "stream/call_data_records.json": "call_data_records.json",
    "stream/money_transfers.json":   "money_transfers.json",
    "saas/zendesk_tickets.json":     "zendesk_tickets.json",
    "batch/financial_payments.csv":  "financial_payments.csv",
}
for src, dst in FILES.items():
    shutil.copy2(SOURCE / src, RAW / dst)

5.2 Configuration du projet dbt

Le profil pointe vers un fichier DuckDB local. Le projet définit une matérialisation par défaut external au format Parquet, fournie par l'adaptateur dbt-duckdb.

# profiles.yml
rebtel:
  target: dev
  outputs:
    dev:
      type: duckdb
      path: ../storage/warehouse.duckdb
      threads: 4

# dbt_project.yml (extrait)
vars:
  storage_root: "../storage"
models:
  rebtel:
    +materialized: external
    +format: parquet

5.3 Déclaration des sources

DuckDB sait lire directement les fichiers JSON et CSV. Les sources dbt pointent donc vers les fichiers bruts, sans étape de chargement en table.

sources:
  - name: raw
    tables:
      - name: raw_stream_cdrs
        config:
          external_location: "read_json_auto('../storage/raw/call_data_records.json')"
      - name: raw_batch_payments
        config:
          external_location: "read_csv_auto('../storage/raw/financial_payments.csv', header = true)"

5.4 Écriture de chaque modèle en Parquet

Une macro calcule le chemin de sortie à partir de la couche et du nom du modèle. Chaque modèle l'appelle dans son bloc de configuration.

{% macro storage_path(layer) -%}
{{ var('storage_root') }}/{{ layer }}/{{ model.name }}.parquet
{%- endmacro %}

-- en tête de chaque modèle
{{ config(location=storage_path('staging')) }}

Les modèles stg_* sont écrits dans staging/, les fct_* et mart_* dans marts/, afin de conserver trois zones de stockage.

5.5 Traduction du SQL BigQuery vers DuckDB

La logique métier (seuils, catégories, scores, jointures) est reprise ligne à ligne. Seules les fonctions propres à BigQuery sont traduites.

BigQueryDuckDBRemarque
COUNTIF(x)count_if(x)Équivalent direct
TIMESTAMP(x)cast(x as timestamp)Équivalent direct
TIMESTAMP_DIFF(b, a, HOUR)floor(date_diff('second', a, b) / 3600)Compte les heures pleines, comme BigQuery. date_diff('hour') compterait les changements d'heure.
CURRENT_TIMESTAMP()current_timestampÉquivalent direct
`projet.dataset.table`{{ ref('table') }}dbt calcule l'ordre d'exécution

Le passage à ref() est l'apport méthodologique principal : l'ordre d'exécution codé à la main dans dbt_runner.py devient un graphe de dépendances calculé, ce qui autorise l'exécution parallèle et la documentation automatique du lignage.

5.6 Tests de qualité de données

Trois fichiers schema.yml (un par couche) déclarent 38 tests. Ils couvrent l'unicité et la non-nullité des clés (call_id, transfer_id, user_id dans les faits, etc.) et les valeurs acceptées pour chaque catégorie calculée.

- name: fraud_risk_level
  data_tests:
    - accepted_values:
        arguments:
          values: [CRITICAL_RISK, HIGH_RISK_FRAUD, MEDIUM_RISK, LOW_RISK, SAFE]

5.7 Rebranchement du modèle d'apprentissage

Le script est copié dans ml/. Seule la lecture des données change : le client BigQuery est remplacé par une requête DuckDB sur le fichier Parquet. Les sorties sont écrites dans storage/ml_outputs/. Les trois modèles comparés (forêt aléatoire, gradient boosting, régression logistique), le découpage 70/30 et les métriques restent identiques.

MART_PATH = os.path.join(STORAGE, "marts", "mart_fraud_prevention.parquet")
df = duckdb.sql(f"SELECT ... FROM read_parquet('{MART_PATH}')").df()

5.8 Rebranchement du tableau de bord

Le tableau de bord Streamlit est copié dans dashboard/. Trois modifications suffisent :

  1. Le client BigQuery et son authentification gcloud sont remplacés par une connexion DuckDB en mémoire, qui crée une vue par fichier Parquet de storage/marts/. La fonction d'accès conserve son nom, si bien que le reste du code (environ 1 700 lignes) n'est pas modifié.
  2. Les noms de tables qualifiés `projet.dataset.mart_x` deviennent mart_x.
  3. Les fichiers bruts sont lus dans storage/raw/ et les libellés affichés mentionnent DuckDB.
@st.cache_resource
def get_duckdb_conn():
    con = duckdb.connect()
    for path in glob.glob(os.path.join(MARTS_DIR, "*.parquet")):
        name = os.path.splitext(os.path.basename(path))[0]
        con.execute(f"CREATE OR REPLACE VIEW {name} AS SELECT * FROM read_parquet('{path}')")
    return con
Défaut corrigéL'onglet ML de l'original utilisait pd.cut avec une borne finale égale au maximum de signaux de fraude plus un. Lorsque ce maximum est inférieur à 8, les bornes ne sont plus croissantes et l'onglet s'arrête sur une erreur. Avec ces données, le maximum vaut 6. La borne a été remplacée par max(max_sig + 1, 9).

7Limites et points de vigilance

Fuite de la cibleLe score F1 de 100 % ne mesure pas une capacité de prédiction. La cible is_fraud est déduite de fraud_risk_level, lui-même calculé à partir de fraud_transfers et fraud_tickets. Or ces colonnes, ainsi que total_fraud_signals qui en est la somme, figurent parmi les variables explicatives. Le modèle retrouve donc une règle qui lui est fournie. S'ajoute un jeu de test de 15 utilisateurs seulement (30 % de 48). Ce défaut vient de l'original et a été conservé pour ne pas modifier la logique métier.
  • Données synthétiques. Les distributions sont uniformes et générées aléatoirement. Les résultats n'ont pas de valeur métier.
  • Ingestion simplifiée. La copie de fichiers ne reproduit ni la latence ni le découpage en micro-lots d'un flux temps réel. Les colonnes techniques d'Airbyte (_airbyte_ab_id, _airbyte_emitted_at) ne sont pas recréées.
  • Plan d'abonnement. latest_subscription_plan reste un maximum alphabétique, faute de date de paiement dans la source.
  • Éléments non migrés. Les vues vw_* et l'intégration Looker décrites dans le README d'origine n'existent pas dans le dépôt.
  • Versions. Le script ML a été exécuté avec succès sous Python 3.14 et sous Python 3.12. Travail réalisé avec Python 3.14, dbt-core 1.11.11, dbt-duckdb 1.10.1, DuckDB 1.5.6, scikit-learn 1.9.1, matplotlib 3.11.2, Streamlit 1.65.0.

8Liste de contrôle pour un nouveau cas d'usage

  • Profiler chaque source : lignes, clés distinctes, types, valeurs des catégories.
  • Comparer le README avec le code réel et noter les écarts.
  • Dresser la table de correspondance cloud vers local.
  • Écrire un requirements.txt et l'installer avec python -m pip install -r requirements.txt, après avoir vérifié l'interpréteur avec sys.executable.
  • Créer storage/raw, storage/staging, storage/marts.
  • Écrire un script d'ingestion idempotent vers raw/.
  • Initialiser le projet dbt avec un profil DuckDB et la matérialisation external.
  • Déclarer les sources avec read_json_auto, read_csv_auto ou read_parquet.
  • Traduire chaque modèle sans toucher à la logique, en remplaçant les noms en dur par ref() et source().
  • Vérifier les fonctions de dates : leur sémantique diffère souvent d'un moteur à l'autre.
  • Ajouter des tests de clés et de valeurs acceptées, puis lancer dbt run et dbt test.
  • Comparer les volumétries avec celles de l'original.
  • Rebrancher les consommateurs (ML, tableaux de bord) en ne modifiant que la couche d'accès.
  • Contrôler l'absence de fuite entre variables explicatives et cible dans tout modèle d'apprentissage.
  • Documenter chaque écart, chaque correction et les versions utilisées.

AAnnexe : commandes d'exécution

Installer les dépendances dans le bon interpréteurLe poste compte plusieurs installations de Python (3.14 et 3.12). Selon le terminal utilisé, la commande python ne désigne pas le même interpréteur. Un paquet installé dans l'un reste invisible pour l'autre, ce qui a produit l'erreur ModuleNotFoundError: No module named 'sklearn' lors d'une exécution depuis PowerShell. La parade consiste à toujours installer avec python -m pip, qui cible l'interpréteur qui exécutera ensuite les scripts, à partir d'un fichier requirements.txt.

Vérifier l'interpréteur utilisé :

python -c "import sys; print(sys.executable)"

Depuis rebtel_local/, installer les dépendances puis lancer l'ingestion :

python -m pip install -r requirements.txt
python scripts/ingest_raw.py

Depuis rebtel_local/rebtel_dbt/ :

dbt run --profiles-dir .
dbt test --profiles-dir .

De nouveau depuis rebtel_local/ :

python ml/ml_fraud_detection.py
python -m streamlit run dashboard/app.py

Le tableau de bord est alors accessible à l'adresse http://localhost:8501. Les dépendances Python sont listées dans rebtel_local/requirements.txt : dbt-duckdb, duckdb, pandas, numpy, pyarrow, scikit-learn, matplotlib, streamlit, plotly.
